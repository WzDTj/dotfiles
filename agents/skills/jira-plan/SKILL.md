# Jira 计划专家

当用户提供 Jira 单号，并希望先理解任务再推进时，使用这个 skill。该 skill 通过本地 Atlassian CLI (`acli`) 获取 Jira 内容，将任务分类为开发、排查或调研，并按分类输出下一步计划。

所有面向用户的输出必须使用中文，包括分类结论、计划标题、步骤、风险、问题和总结。命令、文件路径、代码标识符、Jira 单号和英文专有名词可以保留原文。

## 输入

接受类似 `ABC-123` 的 Jira 单号，也可以接受用户补充的上下文。Jira 内容是主要事实来源，但如果用户明确收窄范围或补充约束，需要一并纳入分析。

如果没有 Jira 单号，只询问一个明确问题：请用户提供 Jira 单号，然后停止。

## 命令探测

不要假设本机安装的 `acli` 版本。首次在新环境中获取 Jira 内容前，先检查本地帮助和登录状态：

```bash
acli --help
acli jira --help
acli jira auth --help
acli jira auth status
acli jira workitem --help
acli jira workitem view --help
acli jira workitem search --help
```

如果本地命令名称或参数与示例不同，以本地 help 输出为准。

## 获取 Jira 内容

优先使用直接 JSON 获取：

```bash
acli jira workitem view ABC-123 --json
```

如果支持字段选择，获取分类和计划所需字段：

```bash
acli jira workitem view ABC-123 --json --fields key,issuetype,summary,status,assignee,description,comment
```

如果无法直接 view，使用 JQL 搜索作为 fallback：

```bash
acli jira workitem search --jql "key = ABC-123" --json --limit 1
```

不要原样倾倒 Jira 描述或评论。尤其当评论可能包含个人信息、凭据、客户信息或内部事故材料时，只提炼工程分析所需的摘要。

## 分类规则

必须选择一个主要分类：开发、排查或调研。

开发任务包括新功能、实现请求、重构、迁移、测试补充、API 行为变更、UI 行为变更、与代码相关的文档变更，或需要代码改动才能满足的验收标准。

排查任务包括 bug、回归、故障、事故、偶发问题、错误日志、失败测试、根因分析、复现步骤，或尚不清楚修复方式的用户反馈。

调研任务包括 spike、可行性分析、方案对比、需求澄清、技术探索、未知方案选择，或产出是建议而不是代码变更的任务。

如果分类信心不足，先用中文说明最可能的分类和原因，并只问一个必要的澄清问题。不要在关键信息缺失时编造计划。

## 开发任务输出

如果判断为开发任务，直接用中文输出计划。除非用户当前消息明确要求实现、修复、修改、创建或构建，否则不要开始写代码。

使用这个结构：

```markdown
**分类**
开发：<一句话说明原因>

**目标**
<要达成的用户可见行为或系统行为>

**Jira 上下文**
<简要总结 issue 类型、标题、状态、关键描述、验收标准和重要评论>

**需要检查的文件**
- <可能相关的文件或模块；如果未知，列出需要做的代码搜索>

**验收标准**
- <从 Jira 提炼出的标准>

**TDD 计划**
- 先新增或确认一个失败测试/表征测试。
- 用最小实现让测试通过。
- 为 Jira 中提到的边界情况补充回归覆盖。
- 如果仓库没有测试体系，明确说明手动验证路径。

**实现步骤**
1. <步骤>
2. <步骤>
3. <步骤>

**验证步骤**
- <具体测试、构建、lint、手动 QA，或明确说明没有测试体系>

**风险和问题**
- <只列阻塞项或会影响方案的关键不确定性>

**原子提交策略**
- <一个聚焦的 commit subject 和应包含的文件组>
```

## 排查任务输出

如果判断为排查任务，不要直接给补丁方案。先用中文输出诊断计划：

```markdown
**分类**
排查：<一句话说明原因>

**现象摘要**
<什么坏了、影响谁、出现在哪里>

**已知证据**
- <日志、截图、评论、受影响版本、环境>

**复现计划**
1. <步骤>
2. <步骤>

**根因排查路径**
- <代码路径、观测查询、git 历史、相关测试>

**确认后的修复方向**
- <最小修复方向，不写未经验证的推测性代码>

**验证步骤**
- <回归测试和手动验证路径>

**开放问题**
- <只列复现或定位根因所必需的问题>
```

## 调研任务输出

如果判断为调研任务，用中文输出带决策标准的调研计划：

```markdown
**分类**
调研：<一句话说明原因>

**调研目标**
<需要做出的决策或建议>

**当前上下文**
<来自 Jira 的摘要>

**需要回答的问题**
- <问题>

**需要检查的信息源**
- <代码区域、文档、历史 ticket、指标、相关负责人>

**评估标准**
- <权衡点、约束、成功标准>

**交付物**
<建议、spike 记录、原型范围或后续 Jira 拆分>

**风险和未知项**
- <关键不确定性>
```

## 安全和范围

除非用户明确要求产生外部副作用，否则不要创建 Jira 评论、流转状态、分配 issue 或修改远端状态。

不要暴露 Jira 中的密钥、客户信息或个人敏感信息。只在工程工作所需粒度上总结敏感细节。

不要编造验收标准。如果 Jira 信息不足以生成计划，用中文说明缺失内容，并只问一个精确问题。

不要从分析自动进入实现。只有当用户当前消息明确要求实现、修复、修改、创建或构建时，才可以进入代码改动。
